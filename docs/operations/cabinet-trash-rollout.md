# 3D 캐비넷 휴지통 및 저장 안정성 변경

캐비넷에서 시약·선반을 삭제하면 휴지통으로 이동한다. 삭제 시각부터 240시간 동안 복원할 수 있으며, 만료 시 복원을 차단하고 삭제 처리기가 연결 재고와 복원 데이터를 제거한다. 삭제된 UUID 목록은 오래된 클라이언트가 데이터를 다시 생성하지 못하도록 남긴다. 기존 시약 사용·폐기 절차와 캐비넷 전체 삭제 정책은 별도 흐름을 유지한다.

## 적용 파일과 순서

1. `supabase/migrations/20261002000000_cabinet_trash_and_revision.sql`을 스테이징에서 검증한 다음 승인된 배포 절차로 적용한다. 기존 기준 스키마를 원격에서 다시 실행하거나 데이터베이스를 초기화하지 않는다.
2. 신규 RPC를 사용하는 프런트엔드와 `functions/api/internal/deletions/_processor.ts`를 함께 배포한다. 이전 전체 저장 RPC의 authenticated 실행 권한은 제거되므로 이전 클라이언트의 새로고침이 필요하다.
3. 기존 deletion scheduler가 해당 환경의 처리 API를 호출하는지 확인한다. production 설정은 매분 실행이며, 임대 잠금을 확보한 처리기가 계정·연구실 삭제 요청이 없어도 휴지통 정리를 실행한다. 정리 실패 시 오류가 반환되고 임대 잠금은 해제된다.
4. 스테이징에서 시약 삭제 → 활성 재고에서 숨김 → 휴지통 복원 → 동일 UUID 및 재고 연결 유지, 선반 삭제·원래 순서 복원, 동시 저장 충돌 차단, 만료 후 복원 차단 및 정리 재시도를 확인한다. 다른 연구실 재고는 연결·복원·정리 대상이 되지 않아야 한다.

만료 데이터는 처리기 실행 시 제거된다. 처리기가 중단되면 물리적 제거가 지연되지만, 만료 즉시 사용자에게 숨겨지고 복원은 차단된다. 복원 공간이 부족하거나 캐비넷이 변경된 경우 전체 트랜잭션을 취소하고 휴지통 데이터를 유지한다.

## 함께 수정한 동작

- 캐비넷·선반·시약을 동일 스냅샷으로 불러오고 버전과 명시적 삭제 ID를 검사한다. 로딩 실패·캐비넷 전환·오래된 응답으로 기존 데이터를 덮어쓰지 않는다.
- 편집 내용, 연결 재고 메타데이터, 서버에서 산출한 감사 기록을 하나의 저장 트랜잭션으로 반영한다. GHS 응답은 캐비넷·시약·CAS·이름이 일치하는 항목에만 부분 반영한다.
- 실제 모델 크기에 맞춰 벽·깊이·칸막이·높이·시약 간 충돌을 클라이언트와 서버에서 확인한다.
- 캐비넷 크기 변경과 모드 전환 시 카메라 및 선반 포커스를 갱신한다.
- HDR 환경광을 로컬 자산으로 제공하고 내부 보조광을 추가했다. 환경광·개별 모델 로딩 실패를 격리하고 모델 재시도를 제공한다. 그림자 계산 횟수와 화면 해상도를 제한하고 복제 재질을 해제한다.

### 현재 Ops가 막는 이유

전체 단위 검사 최종 기록은 1,600개 통과, 7개 건너뜀, 9개 실패다. 실패 중 3개는 `verify-database-release-safety.mjs`가 활성 마이그레이션을 과거 9개로 고정했기 때문이다. 실제로는 재고 가져오기와 캐비넷 SQL까지 11개다. 나머지 6개는 과거 준비 단계의 Git 범위 검사에서 발생했다. `git diff --name-only`와 `git ls-files --others`를 줄 단위로 읽으면 한글 경로가 Git의 따옴표·역슬래시·8진수 표현으로 반환돼 `malformed`로 오판정된다. 경로 수집은 `-z`와 NUL 분리로 수정해야 하며, 디코딩된 IR·다른 작업 경로도 그 뒤에는 정확한 범위 검사로 거부해야 한다. 전역 `core.quotepath` 변경이나 광범위한 경로 예외로 처리하지 않는다.

Quality 워크플로는 전체 단위 검사, DB 경계 검사, 브라우저용 Ops 범위 검사를 실행한다. Staging·Production 배포는 같은 SHA의 성공한 Quality 실행을 요구한다. 따라서 현재 실패는 실제 배포 조건을 막는다. 사람이 별도 거절했거나 공급자 API가 배포를 거절한 결과는 아니다. 원격 GitHub 실행 상태는 이번 로컬 검토에서 조회하지 않았다.

### 허용 목록 갱신 전 해결할 사항

1. **DB 권한 계약:** 새 로컬 PG17 빈 DB에서 공개 테이블 53개, RLS 53개, anon 권한 대상 24개, authenticated 36개, 명시적 service_role 권한 대상 50개를 확인했다. 재고 가져오기 테이블 `inventory_import_jobs`, `inventory_import_rows`, `inventory_import_profiles`에는 service_role GRANT가 없다. BYPASSRLS는 테이블 권한을 부여하지 않는다. 새 증분 SQL로 권한을 명시하고, 실제 Supabase에서 예상치와 비교해야 한다. 이미 적용됐을 수 있는 기존 import SQL을 제자리 수정하지 않는다.
2. **SQL 검사 연결:** 기존 `supabase/tests/baseline_permissions.sql`은 공개 테이블 49개, authenticated 32개, service_role 49개를 기대한다. 현재 최종 스키마에는 맞지 않는다. 새 릴리스에서 검토한 최종 스키마·권한 pgTAP와 import·cabinet 권한 시험을 추가하고, CI가 모든 활성 pgTAP를 실행하도록 변경해야 한다. 현재 Quality는 baseline 파일 하나만 실행한다. 기존 기반 SQL·운영 이력의 고정 해시는 유지한다.
3. **휴지통 자동 정리 활성화:** Scheduler의 `maintenance_worker_enabled`와 API의 `runtime.maintenanceEnabled`가 OFF이면 purge가 실행되지 않는다. 현재 원격 KV 상태는 미확인이다. 동일 후보의 Staging 검증과 예약 호출 성공 기록, 운영 적용 순서와 자동 OFF 시 복구 절차가 필요하다. 계정 삭제 접수 활성화와 유지보수 실행은 구분하고, 휴지통을 출시하기 위해 계정 삭제 접수를 함께 켜지 않는다. 만료 즉시 복원은 차단되지만 Worker 중단 시 물리적 제거는 지연된다.
4. **기존 클라이언트 호환성:** 캐비넷 SQL이 이전 저장 RPC의 authenticated 실행 권한을 제거한다. 마이그레이션만 먼저 적용하고 이전 프런트엔드를 방치하면 저장이 실패한다. 새 RPC 도입·새 클라이언트 전환·구 RPC 권한 제거의 배포 순서를 검증해야 한다. 이전 앱으로 단순 롤백하는 것은 안전한 복구 방법이 아니다.
5. **후속 검사 계약:** 과거 Ops 준비 단계의 전체 작업 트리 검사를 새 후보 통과 조건으로 재사용하지 않는다. 새 기준 SHA, 정확한 변경 파일 목록, SQL·권한 검사 해시를 갖춘 후속 계약으로 연결하고 미승인 파일·해시 변경·경로 탈출을 계속 거부한다. 과거 준비 단계의 순수 보안·부정 회귀 검사는 유지한다. Ops12 사진 정리, 기준선 재실행, 원격 reset, 같은 SHA의 Quality·Staging·백업 조건을 완화하지 않는다.

검토 중 캐비넷 SQL에 `lock_timeout='5s'`, `statement_timeout='60s'`를 추가했다. 이후 독립 로컬 DB 재구성과 캐비넷 fixture가 다시 통과했다. 전체 pgTAP, Hosted Storage·REST, 원격 스케줄러와 실제 AI 모델 검증을 통과한 것으로 간주하지 않는다.

검토한 SQL의 SHA-256은 CRLF를 LF로 정규화해 계산했다.

| SQL | SHA-256 |
|---|---|
| `20260922010000_inventory_import_v2.sql` | `93cf5cd008146a6d9b0e16b4d2f5d11fbdfa32fc0d2d12288cf96451f8248808` |
| `20261002000000_cabinet_trash_and_revision.sql` | `00c861587724a8f881a95be582e62591a843dd8fd178b3439f931bd274b02b40` |

위 항목 때문에 검토 판정은 **후속 범위 확정, 출시 차단 사항 있음**이다. 실패를 숨기거나 기존 검사의 반환값을 성공으로 바꾸지 않았다.
