# 3D 캐비넷 휴지통 및 저장 안정성 변경

## 2026-10-14 휴지통 저장 오류 수정

### 후속: 원래 위치 복원과 빈 공간 탐색

삭제 수정 후 복원에서도 전체 캐비넷을 검증해 같은 오류가 발생했다. 보고된 휴지통 시약의 원래 좌표 자체에는 충돌이 없었으며, 운영의 읽기 전용 위치 탐색으로 원래 선반·가로·깊이 좌표가 모두 유지됨을 확인했다.

`20261014081429_cabinet_restore_nearest_space.sql`은 복원할 시약만 기존 시약·벽·칸막이·선반 높이에 대해 검사한다. 원래 좌표를 우선하고, 막혀 있으면 같은 선반에서 물리적 거리가 가까운 빈 공간, 다른 선반 순서로 탐색한다. 원래 선반이 없어진 경우도 다른 선반을 사용할 수 있다. 고정 격자 대신 장애물 경계 좌표를 사용한다. 기존 시약은 옮기지 않으며 복원 배치 중 하나라도 놓을 수 없으면 트랜잭션 전체를 취소해 휴지통·재고 연결·버전을 보존한다. 선반 복원으로 높이가 줄어드는 경우 기존 시약의 높이도 검증한다. 기존 모델 크기와 충돌 여유 수치는 유지했다.

스테이징에서 기존 함수의 오류를 재현한 뒤 수정했다. 로컬 전체 캐비넷 SQL fixture, 스테이징·운영의 합성 데이터 회귀 시험이 통과했고 시험 데이터는 모두 롤백했다. 신규 시험은 원래 자리, 점유된 자리의 대체 위치, 다른 선반, 사라진 선반, 부분 복원 방지, 오래된 버전, 다른 사용자 접근을 검증한다. Vitest 30개, 앱 TypeScript와 변경 TypeScript 파일 ESLint도 통과했다. 프런트엔드에는 복원 방식 안내와 공간 부족·버전 충돌·만료 오류 구분을 추가했다. 프런트엔드 운영 배포나 브라우저 클릭 검증은 이번 작업에 포함하지 않았다.

MCP 적용 이력: 스테이징 `20261014081346`, 운영 `20261014081429`, 이름 `cabinet_restore_nearest_space`. 로컬 파일명은 운영과 일치하며 스테이징의 버전 차이는 후속 CLI 배포 전에 조정해야 한다. private 탐색 함수의 authenticated 실행 및 공개 복원 함수의 anon 실행은 불가하고, 보안 advisor 항목 수는 변경 전후 동일하다.

운영 PostgreSQL 로그에서 `save_cabinet_state_v2`의 `CABINET_SPACE_REQUIRED` 오류를 확인했다. 기존 저장 배치에도 겹침이 있어 시약 하나를 제거해도 남은 배치 전체 검증에 실패했다. `20261014080315_cabinet_allow_nonspatial_saves.sql`은 저장 전후의 실제 캐비넷 크기, 선반 구조, 남은 시약의 공간 속성을 비교한다. 삭제·메타데이터 변경·동일 상태 재저장은 허용하고, 시약 추가·이동·크기·모델 변경 및 선반·칸막이·캐비넷 크기 변경에는 기존 공간 검증을 유지한다. 접근 권한, 명시적 삭제 ID, 버전 충돌, 휴지통 보존 및 복원 검증은 유지한다.

로컬 PostgreSQL 17.11의 기존 휴지통 fixture와 신규 `scripts/fixtures/cabinet-nonspatial-assertions.sql`이 통과했다. 스테이징에서는 수정 전 동일 오류를 재현하고 수정 후 통과했다. 운영 적용 후에도 합성 데이터만 사용하는 동일 회귀 SQL이 통과했으며, 시험 데이터는 트랜잭션 전체를 롤백했다. 서비스·스토어 Vitest 20개가 통과했다. 운영 함수의 익명 실행 불가·인증 사용자 실행 가능 권한은 유지됐고, 보안 advisor 항목 수는 적용 전후 동일했다.

MCP 적용 이력: 스테이징 `20261014080248`, 운영 `20261014080315` (이름은 모두 `cabinet_allow_nonspatial_saves`, SQL 내용 동일). 로컬 파일명은 운영 이력에 맞췄다. 후속 CLI 배포 전 스테이징의 이 버전 차이를 조정해야 하며, 같은 변경을 중복 적용하지 않는다. 이번 반영은 저장 함수 하나에 한정되며 기존 출시 차단 사항 전체의 해소를 뜻하지 않는다. 브라우저 조작 재검증은 수행하지 않았다.

## 적용 파일과 순서

1. `supabase/migrations/20261002000000_cabinet_trash_and_revision.sql`을 스테이징에서 검증한 다음 승인된 배포 절차로 적용한다. 기존 기준 스키마를 원격에서 다시 실행하거나 데이터베이스를 초기화하지 않는다.
2. 신규 RPC를 사용하는 프런트엔드와 `functions/api/internal/deletions/_processor.ts`를 함께 배포한다. 이전 전체 저장 RPC의 authenticated 실행 권한은 제거되므로 이전 클라이언트의 새로고침이 필요하다.
3. 기존 deletion scheduler가 해당 환경의 처리 API를 호출하는지 확인한다. production 설정은 매분 실행이며, 임대 잠금을 확보한 처리기가 계정·연구실 삭제 요청이 없어도 휴지통 정리를 실행한다. 정리 실패 시 오류가 반환되고 임대 잠금은 해제된다.
4. 스테이징에서 시약 삭제 → 활성 재고에서 숨김 → 휴지통 복원 → 동일 UUID 및 재고 연결 유지, 선반 삭제·원래 순서 복원, 동시 저장 충돌 차단, 만료 후 복원 차단 및 정리 재시도를 확인한다. 다른 연구실 재고는 연결·복원·정리 대상이 되지 않아야 한다.

만료 데이터는 처리기 실행 시 제거된다. 처리기가 중단되면 물리적 제거가 지연되지만, 만료 즉시 사용자에게 숨겨지고 복원은 차단된다. 복원 공간이 부족하거나 캐비넷이 변경된 경우 전체 트랜잭션을 취소하고 휴지통 데이터를 유지한다.

전체 단위 검사 최종 기록은 1,600개 통과, 7개 건너뜀, 9개 실패다. 실패 중 3개는 `verify-database-release-safety.mjs`가 활성 마이그레이션을 과거 9개로 고정했기 때문이다. 실제로는 재고 가져오기와 캐비넷 SQL까지 11개다. 나머지 6개는 과거 준비 단계의 Git 범위 검사에서 발생했다. `git diff --name-only`와 `git ls-files --others`를 줄 단위로 읽으면 한글 경로가 Git의 따옴표·역슬래시·8진수 표현으로 반환돼 `malformed`로 오판정된다. 경로 수집은 `-z`와 NUL 분리로 수정해야 하며, 디코딩된 IR·다른 작업 경로도 그 뒤에는 정확한 범위 검사로 거부해야 한다. 전역 `core.quotepath` 변경이나 광범위한 경로 예외로 처리하지 않는다.
