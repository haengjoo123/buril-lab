# Ops3 Staging 실제 API·사진 검증

이 검사는 이미 성공한 Staging 배포를 검증할 뿐, Pages·Worker를 배포하거나 운영 설정을 변경하지 않는다. 사용자 승인 범위 안에서 기존 GitHub `staging` 환경 비밀값을 사용한다. 새 PAT, Cloudflare 토큰, Access 토큰 또는 배포 lease는 필요하지 않다.

## 실행 전 조건

- 보호된 `main`에서 `Verify Ops3 Staging live APIs and photo`를 수동 실행한다. 재실행(run attempt > 1)은 거부하며, 새 검증은 새로운 run으로 실행한다.
- 검증 코드의 SHA는 현재 `main`이어야 하며 최신 Quality 검사가 성공해야 한다.
- 대상 runtime SHA는 `main`의 조상이어야 한다. 정확한 성공 Staging run과 해당 run의 서명된 자격값 폐기 영수증을 확인한다.
- `target_commit_sha`, `target_deployment_id`, `staging_run_id`와 `VERIFY OPS3 STAGING <deployment UUID> <full SHA> <Staging run ID>` 확인문구가 정확히 일치해야 한다.
- 실제 요청 전 custom·immutable 주소가 모두 Access로 보호되고 동일한 Staging `release.json`을 반환해야 한다.
- 다른 Staging 배포·합성시험과 같은 `cloudflare-staging` 동시 실행 잠금을 사용한다. 운영용 프로젝트·키·Storage·KV는 접근하지 않는다.

## 검증 범위

1. 신규 AI 3개, 레거시 AI 3개, 음성 3개의 미인증 요청이 JSON 401을 반환한다.
2. 미등록 API 404, 허용되지 않은 메서드 405, 허용되지 않은 Origin 403, 잘못된 연구실 UUID 400, 손상 JSON 400, 본문 크기 초과 413 및 응답 보호 헤더를 확인한다.
3. 메모리에서 만든 가상 물 라벨로 신규·레거시 라벨 분석을 한 번씩 실행한다. 분류·폐기 참고 응답은 `responseSource=ai`만 성공으로 인정하며 캐시·대체 응답을 실제 AI 성공으로 세지 않는다.
4. 폐기 참고 응답은 정보가 부족한 입력을 `needs_input`, `depositAllowed=false`로 유지해야 한다. 음성 폐기는 기존 고정 문구와 검토 화면 열기만 허용한다. 실제 혼합·투입·폐기 기록은 수행하지 않는다.
5. 가상 재고의 위치 요청을 확인한다. 현재 위치 응답에는 AI/대체 경로 구분 필드가 없으므로 이 항목은 응답 계약 검증이며 AI 공급자 사용을 독립적으로 증명했다고 표시하지 않는다.
6. 짧은 가상 문장을 MP3로 읽고 같은 메모리상의 오디오를 업로드해 `gpt-transcribe` 결과를 확인한다. 실제 사용자 음성은 쓰지 않는다.
7. Chromium에서 합성 계정으로 로그인하고 합성 연구실에 시약장을 한 개 만든다. 2400×1600 가상 PNG를 실제 파일 입력으로 올려 WebP, 긴 변 1920px, 2MiB 이하, 업로드/다운로드 SHA-256 일치를 확인한다. 브라우저 CSP 위반과 예상 밖 유료 API 요청은 0이어야 한다.

앱 HTTP 요청은 최대 28회, 유료 처리가 가능한 정상 요청은 최대 9회다. 음성 위치의 별칭 생성처럼 한 서버 요청이 추가 공급자 호출을 포함할 수 있으므로 **공급자 호출 총수가 정확히 9회라는 뜻은 아니다**. 요청 재시도는 하지 않으며 서버 측 기존 제한도 유지한다. 브라우저의 별도 AI·음성 호출은 차단한다.

## 비밀값과 정리

- 서비스 역할 키는 GitHub 실행기의 서버 코드에서만 사용한다. 브라우저에는 테스트 계정 로그인만 제공하며, Access 헤더는 정확한 Staging 주소에만 붙인다.
- 브라우저 동영상·화면 캡처·추적 파일·원문 API 응답·토큰·이메일·사용자 UUID·Storage 경로는 출력하거나 업로드하지 않는다.
- 실행기 임시 디렉터리의 정리 journal에는 비밀값 없이 정확한 run/nonce/소유 범위/기존 음성 행 ID만 기록한다. 파일은 외부 artifact로 공개하지 않는다.
- `finally`에서 새 사진, 가상 시약장, 이번 실행에서 추가된 별칭·실패 피드백, 정확한 nonce의 AI 캐시를 정리한다. 기존 음성 행과 감사 이력은 보존한다.
- 시약장의 다른 재고·폐기·안전 기록 참조가 있거나 소유권이 달라지면 삭제를 거부한다. 상위 디렉터리·버킷 전체 삭제는 하지 않는다.
- 정상·실패 후 `always()` 단계가 남은 정확한 journal을 다시 정리한다. 실행기 자체 소실로 journal을 읽을 수 없으면 성공으로 간주하지 않고 비공개 소유권 증거와 집계로 별도 확인한다.
- 기존 Gate0 합성 계정·연구실·기준 재고·정책은 다음 시험을 위해 유지한다. 일반 사용자 데이터는 정리 대상이 아니다.
- 합성 계정의 refresh 세션을 종료한다. 이미 발급된 access JWT가 즉시 무효화됐다고 주장하지 않는다. 이는 [Supabase 로그아웃 동작](https://supabase.com/docs/guides/auth/signout)에 따른 제한이다.

검증 실패와 정리 성공은 별도로 기록한다. 이 검사가 성공해도 운영 3 배포나 7일 관찰, 운영 4~12가 완료된 것은 아니다.
