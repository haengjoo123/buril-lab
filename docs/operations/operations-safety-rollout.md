## 운영 1 사전 안전값

운영 배포 직전 KV `runtime_config`는 다섯 필드를 모두 가진 아래 값이어야 합니다.

```json
{
  "voice_disposal_mode": "redirect",
  "kosha_content_mode": "link_only",
  "account_deletion_enabled": false,
  "maintenance_worker_enabled": false,
  "storage_backup_enabled": false
}
```

누락·형식 오류·KV 장애 때도 동일하게 더 제한적인 상태로 닫혀야 합니다. 첫 배포 30분 관찰을 통과한 뒤에만 KOSHA를 `full`로 바꾸며, 사진 백업은 운영 2 전까지 계속 OFF로 둡니다. KV 변경 뒤에는 최소 2분 동안 실제 응답을 반복 확인합니다.

2026-08-29에는 30분 관찰과 인증된 운영 OpenAI 시험을 통과한 뒤 KOSHA만 `full`로 전환했습니다. 그때 음성은 `redirect`, 삭제·유지보수·사진백업은 OFF였습니다. 2026-09-03 현재 사진백업의 실제 상태는 위 현재 기준점을 따릅니다.

## 운영 묶음별 원칙

1. 정확한 `main` 전체 SHA를 고정합니다.
2. 같은 SHA의 Quality가 성공해야 합니다.
3. 짧게 유효한 배포 자격값만 GitHub environment에 전달합니다.
4. 같은 SHA를 Staging에 배포하고 고유 URL까지 검증합니다.
5. 임시 자격값을 GitHub와 공급자 양쪽에서 폐기하고 서명된 정리 영수증을 남깁니다.
6. 통과 증거가 있는 SHA만 운영 수동 workflow에 전달합니다.
7. 배포 뒤 30분, 24시간, 7일을 실제 시간으로 관찰합니다. Ops 3~11에서는 이 관찰을 다음 단계와 병행할 수 있습니다.

웹은 직전 검증된 Pages production deployment로 되돌립니다. 음성·KOSHA·백업·삭제는 KV로 제한 상태에 둡니다. DB 문제는 하향 migration 대신 쓰기를 제한하고 전진 수정 또는 검증된 백업 복구를 사용합니다.

## 즉시 되돌림 기준

- 위험한 음성 폐기 행동 지침, 인증 우회, 연구실 간 자료 노출, 비밀값 노출이 1건이라도 발생
- 핵심 기능 확인이 두 번 연속 실패
- 5xx가 10분 동안 1% 이상이면서 20건 이상, 또는 저사용 환경에서 5건 발생

## 현재 금지 상태

- 같은 후보 SHA의 Quality·Staging·Hosted 권한시험 없이 운영에 진입
- 실패한 예약 호출, OFF 상태의 빈 호출, 합성시험을 운영 일일 성공으로 계산
- 89개 이력 exact 검증 없이 기준선 이력 정리 또는 증분 migration 적용
- 음성 `guided`, 예약 호출 3회 전 계정·연구실 삭제 UI 활성화
- 시약장 공개 파일 이동·삭제와 고아 파일 삭제
- SDS·바코드·알림·보고서·파일럿·유료 출시

사용자 소유의 미추적 문서·이미지·발표·`output` 파일은 이 작업의 대상이 아닙니다.
