# 임시 자격값 정리 기록의 서명 보존 전환

2026-09-03 KST. 이 절차는 새 공급자 토큰을 발급하거나 웹·DB·Worker를 배포하는 절차가 아닙니다. 기존 폐기 증거를 보존하며 GitHub의 정리 기록 묶음을 이어가기 위한 운영 도구입니다.

## 왜 필요한가

기존 정리 영수증은 GitHub 변수 하나에 이전 배포의 폐기 증거를 모두 포함했습니다. 변수·서명 데이터의 크기를 제한하기 위해 한 묶음에 32개 lease만 허용하며, Staging이 정확히 이 한도에 도달했습니다.

32개 한도와 서명 데이터 48 KiB 한도는 바꾸지 않습니다. 기존 영수증을 지우거나 bootstrap으로 다시 시작하지 않습니다. 완성된 이전 영수증 원문을 해시로 식별되는 저장소 파일에 그대로 보관하고, 새 영수증이 그 파일의 해시를 서명하도록 합니다.

- 이전 영수증: v3, epoch 0, 32개 폐기 증거와 원래 Ed25519 서명
- 새 영수증: v4, epoch 1, 이전 영수증 SHA-256, 현재 묶음 0~32개 증거
- 다음 전환도 같은 방식으로 이전 완성본을 연결합니다. 최대 16개 보관 묶음 이후에는 다시 검토가 필요하며 자동 한도 확대는 없습니다.

검사는 이전 파일의 서명·내용 해시·환경·번호·완전성·시각·초기 폐기 증거를 모두 확인합니다. 현재와 보관 묶음 전체의 run/lease 중복도 거부합니다. 파일 누락, 변조, 다른 환경 파일, 미완성 묶음, 번호 건너뛰기는 모두 실패입니다.

## 최초 Staging 보관 대상

- 원래 영수증 SHA-256: `2f34d77f5313398a4fdf6e06a9f926306063a7963943e2fc6e6b3b773aae3e77`
- 마지막 run: `33688171606`, lease `2755a02d1af0efbda4497dcec4115f4e`
- 원문: `config/ephemeral-cleanup-epochs/staging/2f34d77f5313398a4fdf6e06a9f926306063a7963943e2fc6e6b3b773aae3e77.json`
- 보관 내용은 이미 폐기된 자격값의 해시, run/SHA/lease, 시각과 서명뿐입니다. 토큰 원문·개인키·사용자 행·로그는 포함하지 않습니다.
- Git 텍스트 파일의 마지막 줄바꿈은 서명 원문에 포함되지 않습니다. 원래 영수증의 서명 바이트나 내용은 바꾸지 않았습니다.

`plan`의 실제 읽기 전용 조회에서 GitHub의 기존 32개 자격값 사용 배포와 이 영수증이 정확히 일치했습니다. 실패한 배포라도 자격값 검사를 통과한 실행이면 반드시 포함했습니다. 단순히 최근 배포만 읽거나 특정 날짜 이전을 무시하지 않습니다. 기존 전체 이력 조회 상한(최대 1,000개 workflow run)과 페이지·중복·미완료 검사도 유지합니다.

## plan과 apply

먼저 영수증 보관 파일, 도구와 회귀시험을 PR로 검토하고 main의 필수 품질검사 네 개를 통과시킵니다. apply는 미반영 변경이 없는 정확한 main에서만 실행할 수 있으며, 변경 직전 main과 Quality를 다시 조회합니다. 기존 공개키와 로컬 Windows DPAPI 개인키를 그대로 사용합니다.

```powershell
node scripts/rollover-ephemeral-cleanup-epoch.mjs plan --environment staging --expected-receipt-sha256 2f34d77f5313398a4fdf6e06a9f926306063a7963943e2fc6e6b3b773aae3e77

node scripts/rollover-ephemeral-cleanup-epoch.mjs apply --environment staging --expected-receipt-sha256 2f34d77f5313398a4fdf6e06a9f926306063a7963943e2fc6e6b3b773aae3e77 --confirmation "ROLLOVER staging 2f34d77f5313398a4fdf6e06a9f926306063a7963943e2fc6e6b3b773aae3e77"
```

plan은 서명 개인키를 열거나 원격 값을 쓰지 않습니다. apply도 공급자 토큰을 만들지 않습니다. GitHub의 기존 로그인으로 읽기 전용 이력 조회를 하고, 로컬 보호 키로 새 정리 영수증을 서명해 정리 변수와 Staging 증거 사본만 갱신합니다. 정상 runtime KV·Access 정책·Storage·운영 배포에는 손대지 않습니다.

두 환경과 저장소에 임시 토큰이나 진행 중인 배포를 뜻하는 pending/grant가 남아 있으면 진행하지 않습니다. acceptance 토큰도 포함합니다. 원본 보관 파일은 정확한 main에서 추적 중이어야 하며, 현재 영수증 해시가 입력 대상과 다르면 멈춥니다. 확인문구는 실행 대상 고정을 위한 장치이며 이미 승인된 동일 작업에 사용자 재승인을 요구하는 뜻이 아닙니다.

## 중간 중단 시 복구

새 영수증은 0건짜리 새 시작점이 아니라 이전 전체 서명 기록에 연결된 증거입니다. 원본 영수증을 지우지 않으므로 전환 중 공급자 자격값이 남거나 기록이 손실되지 않습니다.

| 관찰된 상태 | 처리 |
|---|---|
| 현재 영수증이 입력한 이전 해시와 같음 | 전체 검사를 다시 하고 최초 전환 |
| 새 v4가 저장됐지만 production의 Staging 영수증 사본은 이전 값 | 같은 apply로 정확한 새 영수증 사본만 복구. 재서명하지 않음 |
| 양쪽이 같은 새 v4이며 현재 묶음 0건 | 같은 apply는 멱등 확인으로 완료 |
| 다음 lease가 이미 기록됐거나 무관한 값으로 변경됨 | 이전 apply로 덮어쓰지 않고 중단 |

새 Staging·운영 자격값 발급 전에도 두 Staging 증거 사본의 일치와 전체 GitHub 이력을 확인합니다. 사본 갱신이 미완료이면 새 자격값을 만들 수 없습니다. 기존 bootstrap 명령도 이미 있는 영수증을 덮어쓰지 못합니다. 서명 파일을 삭제하거나 GH 변수만 수동 초기화하는 복구는 금지합니다.

새 epoch를 사용하는 provider journal은 v3로 정확한 epoch 번호와 이전 영수증 해시도 고정합니다. 정상 마감·중간 장애 복구에서 이 정보가 바뀌거나 사라지면 실패합니다. 기존 v3 영수증/v2 journal의 복구도 계속 지원합니다.

## 검증과 남는 작업

회귀시험은 원본 서명 보존, 32+1/32+32개의 전체 이력, 변조·누락·중복·다른 환경, 33번째 초과, 초기화 우회, 실제 GitHub 조회 모사, 잔여 비밀값·pending, 정확한 main/Quality, 저장 응답 유실·부분 사본 복구, epoch journal 정상/장애 마감을 포함합니다. GitHub의 기존 Cloudflare 필수 검사에도 새 시험을 포함합니다.

로컬에서 전체 시험 1,223개 통과·기존 보류 7개, Cloudflare 전용 시험 245개, lint·TypeScript 포함 빌드·클라이언트 비밀값 검사·구성/변경 범위/공백 검사를 통과했습니다. 전체 시험의 Supabase 주소·키는 CI와 같은 가상 값이며 실제 데이터 접근 시험을 대신하지 않습니다. 이 코드에 대한 PR/main 필수 검사와 실제 apply 결과는 별도로 확보해야 합니다.

운영 3의 CSP 수정은 별도 PR #67로 main `56b8c98fb072631daeb6872b53ffcbc182a17b0b`에 병합됐고 PR Quality `33690480239`와 main Quality `33690798018`은 각각 4/4 성공했습니다. 정리 기록 전환 후에도 그 수정과 이 도구를 포함한 새 main SHA를 실제 Staging에 배포·검증해야 합니다. 실패한 이전 Staging 배포를 성공으로 바꾸지 않습니다.

이 문서 작성 시 실제 원격 epoch apply·수정 코드 재배포는 아직 하지 않았습니다. 이후 수행 결과는 별도 SHA·run·영수증 해시로 기록합니다. 운영 일일 백업 2회와 24시간·7일 관찰도 별개의 열린 관문입니다.
