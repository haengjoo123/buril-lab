# Ops10 운영자 역할·MFA 준비

상태: `productionReady: false`, `operatorRolesProvisioned: false`, `operatorAuthModeApplied: false`, `hostedSupabaseAcceptance: false`

이 문서는 운영 1~9가 순서대로 적용되고 각각의 관찰조건을 통과한 뒤 사용할 운영 10 후보를 설명합니다. 이번 준비에서는 실제 Supabase·Cloudflare·GitHub 변경, 운영자 역할 부여, 토큰 생성, Staging 배포, 운영 배포를 수행하지 않았습니다. 삭제 UI와 Scheduler도 계속 OFF입니다.

## 평상시 권한 방식

관리자 API는 더 이상 이메일 문자열만 보고 운영자를 판단하지 않습니다. `OPS_AUTH_MODE=server_roles`일 때 서버가 다음 세 역할과 Supabase 세션의 MFA 단계를 함께 확인합니다.

- `reader`: 피드백, 분석 목록·요약·검색, 안전센터 목록 조회
- `approver`: 피드백 상태, 분석 검토, 안전센터 승인 상태 변경
- `raw_exporter`: 행 단위 분석 내보내기와 안전센터 확인문서의 짧은 서명 URL 발급

한 운영자 계정에 세 역할을 모두 부여한다는 현재 운영 결정을 반영하지만, 각 API는 필요한 역할 하나만 정확히 요구합니다. 역할은 이메일이 아니라 Supabase 사용자 ID에 연결됩니다. 모든 운영자 API는 `aal2` 세션만 허용하며, 비밀번호만 통과한 `aal1` 세션은 역할이 있어도 거부됩니다.

역할 검토 시각과 다음 검토기한을 저장하고, 31일이 지나면 해당 역할을 자동으로 거부합니다. 실제 운영에서는 월 1회 세 역할의 필요 여부를 확인하고 검토기한을 갱신해야 합니다.

## 감사와 원자적 변경

`private.operator_action_audit_v1`에는 요청 ID, 사용자 ID, 역할, 일반화한 행동·대상 종류, 성공·거부 결과, MFA 단계만 저장합니다. 이름, 이메일, 조회 본문, 파일 경로, 토큰, 공급자 원문 오류는 저장하지 않습니다.

- `anon`, `authenticated`, `service_role` 모두 역할표와 감사표를 직접 읽거나 쓸 수 없습니다.
- 서비스 역할도 검토된 `SECURITY DEFINER` RPC만 호출할 수 있습니다.
- 감사표는 추가만 가능하며 수정, 삭제, 전체 비우기는 트리거가 거부합니다.
- 피드백·안전센터·분석 검토 상태 변경은 데이터 변경과 성공 감사기록을 한 DB 작업으로 묶습니다.
- 성공 감사가 저장되지 않으면 데이터 변경도 함께 취소됩니다.
- 조회나 서명 URL은 권한·감사 RPC가 먼저 성공하지 않으면 반환하지 않습니다.

응답의 `X-Request-ID`와 같은 서버 생성 요청 ID를 감사기록에 사용합니다. 미들웨어 요청 ID가 없는 직접 단위시험 환경에서만 새 UUID를 내부 생성하며, 클라이언트가 보낸 요청 ID는 신뢰하지 않습니다.

## 긴급 이메일 복귀 모드

이메일 허용목록은 평상시 경로가 아닙니다. 긴급 복귀가 꼭 필요할 때만 다음 값을 모두 명시해 `OPS_AUTH_MODE=email_allowlist`로 잠시 전환할 수 있습니다.

- 일반 운영자 이메일 목록
- 원자료용 별도 이메일 목록
- 현재부터 24시간 이내인 UTC 만료시각
- 8~200자의 복귀 사유

만료, 24시간 초과, 사유 누락, 이메일 불일치, 알 수 없는 모드는 모두 닫힙니다. 이 모드도 `aal2`가 필요하고 서버 감사 RPC를 반드시 통과합니다. 복귀 종료 뒤에는 `OPS_AUTH_MODE=server_roles`로 되돌리고 이메일 목록·만료·사유 비밀값을 제거합니다.

## 로컬 검증 결과

검토한 PostgreSQL 17.11 공식 Windows 바이너리로 서로 다른 빈 DB 두 곳을 만들고 기준선부터 Ops10까지 순서대로 적용했습니다. 합성 사용자와 합성 피드백만 사용했고 원격 호출은 0회였습니다.

- 빈 DB 설치 2회와 카탈로그 권한 검증 성공
- 세 역할의 서비스 전용 부여와 일반 사용자 직접 RPC 거부
- 역할 없음, MFA 없음, 월간 검토 만료 거부 및 감사 성공
- 알 수 없는 행동·역할 조합 거부
- 긴급 이메일 복귀 경로도 MFA 필수 확인
- 감사 수정·삭제·전체 비우기 거부
- 성공 감사 저장 실패를 유도했을 때 상태 변경까지 원복
- 관리자 API 단위시험, 타입검사, lint, 전체 빌드용 경계검사 통과

이 결과는 `hostedSupabaseAcceptance: false`입니다. 실제 운영자 MFA 등록·복구, Hosted Supabase Security Advisor, Staging API, 역할 부여와 이메일 목록 제거는 아직 검증하지 않았습니다.

## 순차 적용과 통과조건

1. 운영 9의 Staging·운영 적용과 7일 관찰이 끝났는지 확인합니다.
2. 같은 후보 SHA에서 빈 DB 두 번, pgTAP, 전체 앱 시험·빌드·패키지 보안검사를 다시 통과합니다.
3. Staging에 migration과 서버 역할 API를 적용하고 지정 운영자에게 세 역할을 부여합니다.
4. MFA 미완료 세션의 모든 민감 API가 403이고, MFA 완료 세션만 역할 범위 안에서 성공하는지 확인합니다.
5. 감사 실패 시 변경과 민감 응답이 모두 닫히고, 다른 사용자가 역할·감사표에 접근할 수 없는지 확인합니다.
6. MFA 기기 분실 복구를 시험하고 실제 비밀값이나 복구코드를 증거 문서에 남기지 않습니다.
7. Hosted Advisor의 새 차이가 0이고 선행 운영 묶음 관찰이 끝난 뒤에만 운영에 적용합니다.
8. 7일 안정화 뒤 이메일 허용목록 비밀값을 제거하고 평상시 `server_roles`만 허용합니다.

문제가 생기면 관리자 API를 보수적으로 닫고, 역할·감사표를 삭제하거나 하향 migration을 실행하지 않습니다. 긴급 복귀는 24시간 이내 만료와 사유를 가진 이메일 모드만 사용하고, 종료 뒤 원인을 기록한 전진 수정으로 돌아옵니다.
