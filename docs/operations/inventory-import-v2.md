# 통합 재고 가져오기 V2

기존 장부를 원본과 함께 초안으로 보관하고, 확인할 항목을 묶어서 수정한 뒤 새 재고로 등록한다. 기본 플래그는 OFF다. 운영 DB 적용, Cloudflare 배포, 유료 AI 호출은 이번 개발 검증에 포함하지 않았다.

## 동작과 구성

- `src/features/inventory/InventoryImportModal.tsx`: 여러 자료 추가, 작업 재개, 표/열 연결, 문제 종류·원본 위치명별 필터, 빈 수량/0/위치/선택 필드/중복 후보 일괄 처리, 행 편집, 등록 요약.
- `src/features/inventory/import/`: 공통 타입, Worker의 파일 읽기·표 후보 탐색, 순수 검증, PDF 텍스트·좌표/이미지 처리. SheetJS CE 공식 0.20.3과 코드페이지를 고정했고 ExcelJS 내보내기는 유지했다.
- `src/services/inventoryImportService.ts`: 비공개 원본 저장, 500행 단위 초안 조회, 100행 단위 저장·등록, 낙관적 버전 검사, 불확실한 저장 요청의 동일 ID 재시도, 등록 영수증 확인.
- `functions/api/ai/inventory-import.ts`: 인증과 작업 RLS 확인 후 저장된 원본만 분석한다. 열 연결은 최대 60열·대표 8행, 문서 분석은 페이지/영역별로 요청한다. AI는 재고를 직접 생성하지 않는다.
- `supabase/migrations/20260922010000_inventory_import_v2.sql`: 작업/행/연구실 양식, 재고 추가정보, RLS, Storage 정책, 저장/일괄 등록 RPC, 기존 계정·연구실 삭제 Worker와 연결.

입력은 XLSX, XLS, CSV, TSV, PDF, JPG/JPEG, PNG, WebP, 카메라 촬영이다. HWP/DOCX는 PDF 변환 경로를 안내한다. 모든 시트를 읽으며 숨김 시트는 기본 제외하고 사용자가 포함할 수 있다. 세로·가로 장부, 반복 표, 나란히 배치된 표, 다단 제목을 제안한다. 원본 미리보기의 행 번호로 제목 행을 고르거나 범위/방향을 직접 바꿀 수 있다. 복잡한 표 탐색은 휴리스틱이며 확정된 표 구조로 보장하지 않는다.

수량의 실제 숫자 0, 소수, 천 단위 구분자를 보존한다. 숫자 셀이 정수처럼 표시돼도 소수를 잘라내지 않는다. 제품번호는 표시값의 앞자리 0을 보존한다. 병합 관계만 전파하고 일반 빈칸은 채우지 않는다. CSV 인코딩은 UTF-8/UTF-16/CP949를 읽고 불확실한 판별은 확인 상태로 남긴다. 수식은 저장된 계산 결과를 사용하며 결과가 없거나 오류 셀이면 확인 대상으로 남긴다.

PDF.js의 문자표·표준 글꼴·이미지 디코더는 앱 빌드에 포함되며 외부 CDN을 사용하지 않는다. 텍스트와 정렬된 제목이 명확한 PDF는 코드로 추출한다. 그 외 PDF와 사진은 원본 저장 후 AI 분석을 시도하며, 실패/비활성화 시 저장된 페이지에서 재시도할 수 있다. 이미지 영역은 위/아래로 나누어 다시 분석할 수 있다.

사진·PDF·손글씨 결과는 전부 원본 확인 전 초안이다. 페이지 단위 확인이 가능하지만 수량·CAS·날짜 오류는 별도로 해결해야 한다. AI의 자체 신뢰도나 자체 행 수 보고만으로 자동 승인하지 않는다. 누락 가능성은 원본과 함께 표시한다. CAS·수량·날짜·위험성을 외부 지식으로 추정하지 않는다.

위치가 없어도 등록할 수 있으며 시약장을 연결해도 병 모양·선반·3D 배치를 요구하지 않는다. 추가정보에는 연결하지 않은 열을 포함한 원본 열/값/주소가 남고, 재고 상세와 XLSX/CSV 내보내기에 포함된다. 현재 앱에 없는 농도·순도·Lot 등은 추가정보로 유지한다. 기존 재고를 자동 합산/갱신/덮어쓰지 않는다.

## 재개와 저장 보장

분석 완료 시점과 원본/표 변경 시점에 서버 초안을 저장한다. 행 편집은 ‘수정 저장’이나 모달 닫기로 저장한다. 처리 중 닫기는 현재 단계를 저장한 뒤 중단 요청으로 동작하며, 저장 중에는 편집을 잠근다. 브라우저/앱을 강제 종료한 시점의 아직 저장되지 않은 입력까지 복구하는 오프라인 편집기는 아니다. 서버가 백그라운드에서 계속 분석하지 않는다.

각 초안 저장 묶음마다 버전과 요청 ID를 기록한다. 응답을 받지 못한 동일 요청은 같은 ID로 재시도하며, 다른 탭이 변경한 버전을 덮어쓰지 않는다. 저장한 묶음은 즉시 체크포인트로 반영한다. 등록은 작업+행을 잠그고 재고 생성·추가정보·영수증을 같은 트랜잭션에 기록한다. 행별 저장 실패는 개별 롤백하고 오류를 초안에 남긴다. 영수증은 재고를 나중에 삭제해도 남으므로 재시도가 해당 재고를 다시 만들지 않는다. 다른 탭에서 등록이 끝난 행·표·원본 영역의 변경도 서버에서 거부한다. 충돌 시 미저장 수정 취소를 명시적으로 선택해 서버 초안을 다시 열 수 있다. 이미 등록한 표/영역의 매핑과 재분석은 잠기며 남은 행의 값은 수정할 수 있다.

계정 삭제는 개인 초안과 개인 원본을 삭제 대상으로 잡고 연구실 공유 초안은 유지한다. 연구실 삭제는 해당 연구실 초안과 원본을 함께 처리한다. 먼저 원본 경로를 기존 삭제 큐에 기록하고, 실제 바이트 제거는 기존 Storage API Worker가 수행한다.

## 제한

- 원본 파일당 20MB, 작업당 원본 합계 100MB, 10,000행, 문서 페이지/분할 영역 합계 50개.
- 메모리 보호를 위해 스프레드시트 확장 영역 100만 셀, 초안 원본 메타데이터 40MB, 저장 행당 256KB 상한도 적용한다. 큰 장부/불필요한 서식 영역은 분할하도록 오류를 반환한다.
- 한 번의 AI 문서 출력은 최대 150행·60열이며 초과/잘린 출력은 확인 또는 영역 분할 대상으로 처리한다. 해당 페이지를 조용히 성공으로 간주하지 않는다.
- 표 없는 목록·판독이 어려운 손글씨·복잡한 줄바꿈 표는 AI 초안 및 수동 확인이 필요하다. 모든 서식을 자동 인식한다는 보장은 없다.

## 활성화 순서

1. 기존 Ops5~Ops11 적용 순서와 삭제 Worker 준비 조건을 먼저 충족한다. 기존 운영 DB에 기준선 SQL을 다시 실행하지 않는다.
2. 새 증분 SQL을 별도 Staging 검증/배포 검토 대상으로 추가한다. 기존 Ops11의 고정 파일 목록·마이그레이션 해시·배포 검사를 임의로 완화하지 않는다. 현재의 과거 배포 묶음 검사에는 이 신규 변경이 포함되어 있지 않다.
3. 비공개 `inventory-imports` 버킷과 RPC/RLS를 실제 Supabase Storage/REST로 검증한 뒤 `VITE_ENABLE_INVENTORY_IMPORT_V2=true`로 클라이언트를 빌드한다. 기본값은 false이며 기존 가져오기 화면으로 돌아갈 수 있다.
4. 사진 시범 적용 시 서버에 `INVENTORY_IMPORT_AI_ENABLED=true`, 기존 OpenAI 키/안전 식별자 설정을 적용한다. 가져오기 전용 설정은 아래와 같다. 다른 AI 기능의 기본값은 바꾸지 않는다.

| 서버 설정 | 기본값 / 상한 |
|---|---|
| `OPENAI_INVENTORY_IMPORT_MODEL` | 빈 값이면 기존 `OPENAI_RESPONSES_MODEL` 상속 |
| `OPENAI_INVENTORY_IMPORT_TIMEOUT_MS` | 60,000ms / 5,000~60,000 |
| `OPENAI_INVENTORY_IMPORT_MAPPING_TOKENS` | 3,000 / 1,000~6,000 |
| `OPENAI_INVENTORY_IMPORT_DOCUMENT_TOKENS` | 16,000 / 2,000~20,000 |

서버 자동 재시도는 0회다. API의 기존 인증/요청 제한/사용자별 호출 제한이 적용된다. GitHub 배포 작업을 통해 기능을 켤 때는 현재 배포 묶음 검토와 함께 클라이언트 빌드 환경에도 공개 플래그를 전달해야 한다. 서버의 AI 플래그와 키를 클라이언트 환경에 노출하지 않는다.

## 검증과 시범 운영

자동 회귀는 숫자 0·1,000·소수·표시 반올림, 중복 제목, 30행 이후 제목, 다중 시트, 병합/다단 제목, 가로/반복/병렬 표, 캐시 수식, 앞자리 0, 인코딩, 날짜/CAS, 추가정보, 문서 원본 확인, 저장 재시도·1,000행 초과 조회·불완전 영수증을 다룬다. 10,000행 파싱 및 초과 거부도 검사한다.

로컬 PostgreSQL 검증은 새 빈 클러스터에 기존 마이그레이션과 새 SQL을 적용한다. 10,000행을 100행씩 저장·등록하고 재시도해 누락/중복이 없는지 검사한다. 개인 간 RLS·원본 접근, 버전 충돌, 행별 실패, 동시 등록, 계정/연구실 삭제 큐도 검사한다. Supabase Auth/Storage 스키마는 로컬 모의 구현이므로 Hosted Storage API 검증을 대체하지 않는다.

```powershell
npm exec -- vitest run src/features/inventory/import/import.test.ts src/services/inventoryImportService.test.ts src/utils/readAllPages.test.ts functions/api/ai/inventory-import.test.ts
node scripts/test-inventory-import-db.mjs <로컬-PostgreSQL-bin-디렉터리>
npm run build
```

브라우저 검증은 실제 Worker와 UI에 가상 500행 CSV를 업로드하고 500건 등록·재개 및 375px 레이아웃을 확인했다. 저장소는 로컬 모의 서비스이며 운영 데이터/유료 AI를 호출하지 않는다. 오류 자료의 0 제외·빈 수량 적용·같은 원본 위치명 연결을 확인했다.

2페이지 인쇄형 PDF 실파일에서는 8행을 추출하고 페이지 단위 확인 전에는 등록할 수 없는 동작을 확인했다. 관련 검사 9개 파일/85개 테스트, TypeScript, 변경 파일 ESLint, 앱 빌드와 클라이언트 비밀값 검사는 통과했다. 전체 회귀 실행 기록은 1,581개 통과/7개 건너뜀/9개 실패이며 이후 2개의 재고 조회 회귀를 추가했다. 실패는 기존 `verify-database-release-safety`, `verify-accelerated-ops3-11-release`, `verify-ops3-release-scope`, Ops5~9 및 Ops11 준비 단계의 파일 목록/작업트리 고정 검사다. 새 마이그레이션은 기존 활성 목록에 등록되지 않았고 현재 작업트리도 과거 배포 묶음과 다르다. 이 결과를 배포 준비 완료로 해석하지 않는다.

시범 운영에서 원본 장부와 사진을 사람이 라벨링한 기준 자료로 비교한다. 인쇄물 행 추출 재현율 95%, 확인 불필요 핵심 필드 정확도 99%는 **출시 목표이며 아직 측정된 성과가 아니다**. 손글씨는 확인 대상으로 유지한다. 회전·흐림·다중 페이지·표 없는 목록과 모바일 카메라는 실제 자료로 별도 평가한다.

수정 건수는 저장된 `draft.fields`와 `draft.originalFields`의 차이, 등록 실패는 `draft.error`, 등록 건수는 `committed_at`으로 측정할 수 있다. 작업 생성부터 마지막 등록까지의 벽시계 시간에는 중단 시간이 포함되므로 실제 작업 시간과 구분한다. AI 구조화 로그 `inventory_import_mapping`, `inventory_import_document`, `inventory_import_analysis_failed`에는 모델·토큰 사용량·소요 시간·행 수/완료 여부가 남고 원본 내용은 로깅하지 않는다. 현재 모델 가격을 적용해 비용을 집계한다.

엑셀 전체를 AI 파일 입력에 맡기지 않는다. 구현 근거: [SheetJS 공식 배포](https://docs.sheetjs.com/docs/getting-started/installation/frameworks/), [PDF.js](https://mozilla.github.io/pdf.js/examples/), [OpenAI 파일 입력의 스프레드시트 처리 범위](https://developers.openai.com/api/docs/guides/file-inputs).
