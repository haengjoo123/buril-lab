# 검색창 에이전트 모드 출시 절차

상태: 1단계(틀과 기본 조회), 2단계(안전·규제 현황과 재고 목록), 3단계(측정), 4단계(기록 제안), 5단계(폐액 배치 한 문장 구성) 구현, 미배포. 빌드 플래그와 런타임 스위치 모두 꺼짐. 3단계 migration은 Staging(이력 `20261126210743`)과 운영(이력 `20261126211223`)에 적용 완료(2026-11-27). Advisor 기준은 두 환경 모두 88건으로 갱신했고, 이어서 적용한 실험도구 migration(`20261127090000`)으로 90건이 되었다. 이 기준이 main에 병합되기 전에는 main에서 하는 Staging·운영 배포의 Advisor 검사가 실패한다.

플래그: `VITE_ENABLE_AGENT_MODE` (기본 꺼짐)
런타임 스위치: 환경별 `BURILLAB_RUNTIME_CONFIG` KV의 **별도 키** `agent_mode_config` (없으면 꺼짐)
DB: 3단계 `supabase/migrations/20261127080000_agent_query_events.sql` (테이블 `agent_query_events`, 함수 `record_agent_query_event_v1`). 1·2단계는 변경 없음

## 기능

메인 검색창에 `검색 | 에이전트` 전환이 생긴다. 검색 모드는 지금과 같다.

에이전트 모드가 처리하는 요청:

| 요청 | 예 | 필요한 조건 |
|---|---|---|
| 시약 하나의 위치·잔량·유효기한 | "아세톤 어디 있어?" | 없음 |
| 만료·임박 시약 목록 | "유효기한 지난 시약 보여줘" | 없음 |
| 화면 열기 (재고, 시약장, 관리자, 일상점검, 구매 요청) | "재고 화면 열어줘" | 화면별 플래그·권한 |
| 부족해 보이는 시약 | "곧 떨어질 시약 알려줘" | `VITE_ENABLE_PURCHASE_REQUESTS` |
| 화학물질관리법 규제 대상과 지켜야 할 일 | "규제 대상 시약 알려줘" | `VITE_ENABLE_REGULATION_BATCH` |
| 잠금 확인이 필요한 시약장 | "잠금 필요한 시약장 있어?" | `VITE_ENABLE_CABINET_LOCK_RULES`, 연구실 |
| 일상점검 누락 | "점검 빠진 날 있어?" | `VITE_ENABLE_DAILY_INSPECTION`, 연구실 |
| 구매 요청 현황 | "구매 요청 현황 알려줘" | `VITE_ENABLE_PURCHASE_REQUESTS`, 연구실 |
| 이번 주 확인할 일 | "이번 주 할 일 알려줘" | 연구실 관리자 |
| 폐액통 현황 (AI 없이 규칙으로) | "폐액통 현황 알려줘" | `VITE_ENABLE_WASTE_CONTAINERS` |
| 기간별 폐기 기록 요약 (AI 없이 규칙으로) | "지난달 폐기 기록 요약해줘" | 없음 |
| 남은 양·다 쓴 병 기록 제안 | "아세톤 30% 남았다고 기록해줘" | KV `mode: actions` |
| 입고 등록 제안 (등록 창을 채워서 엶) | "아세톤 500mL 2병 입고했어" | KV `mode: actions` |
| 구매 요청 제안 | "에탄올 2병 구매 요청해줘" | KV `mode: actions`, `VITE_ENABLE_PURCHASE_REQUESTS`, 연구실 |
| 폐액통 수거 요청 제안 (AI 없이 규칙으로) | "폐액통 수거 요청해줘" | KV `mode: actions`, `VITE_ENABLE_WASTE_CONTAINERS` |
| 폐액 배치 구성 제안 (AI 없이 규칙으로) | "아세톤 200mL랑 메탄올 100mL 섞은 폐액" | 없음 |

- 물질 정보 질문은 일반 검색으로 넘긴다.
- 앱은 조건이 맞는 기능만 서버에 알린다. 조건이 안 맞는 기능은 AI가 고를 수 없고, 앱도 실행 직전에 조건을 다시 확인한다.
- "이번 주 확인할 일"은 관리자 화면과 같은 함수·같은 문구로 만든다. 숨겨 둔 일은 빼고 건수만 알려 준다.
- 일상점검은 빠진 날짜만 알려 준다. 점검 항목의 답을 채우거나 제안하지 않는다.
- 규제 대상 목록은 CAS가 없는 품목 수와 아직 조회되지 않은 수를 함께 보여 준다. "규제 대상 아님"으로 읽히지 않게 하기 위해서다.

검색 모드에서 문장을 입력하면 "에이전트에게 묻기"를 제안만 하고, 스스로 전환하지 않는다.

### 기록 제안 (4단계)

- **제안은 아무것도 저장하지 않는다.** 카드에 무엇을 저장할지 한 문장으로 적고, 사용자가 버튼을 눌러야 저장한다. 저장은 기존 화면과 같은 서비스 함수로 한다(`inventoryService.updateItemUsage`, `recordUsageCompletion`, `createPurchaseRequest`, `requestWasteContainerPickup`). 취소하면 카드가 사라지고 남는 것이 없다.
- **일치하는 품목이 여럿이면 고르지 않는다.** 사용자가 고르기 전에는 버튼이 눌리지 않고, 그 이유를 카드에 적는다. 하나만 일치하면 그 품목이 선택돼 있다.
- **수치는 사용자가 입력한 것만 쓴다.** 남은 양(%)·수량·용량은 요청 문장에 그 숫자가 있을 때만 계획에 남는다. 없으면 카드에서 고르게 한다. 시약 이름과 CAS 번호 규칙은 조회와 같다.
- **다른 연구실로 옮겼으면 저장하지 않는다.** 제안은 만들어진 공간(연구실 또는 개인)을 기억하고, 저장 직전에 현재 공간과 다르면 거부한다.
- "다 쓴 병" 기록은 시약장 선반에 놓인 병만 할 수 있다(기존 사용 완료 경로가 그 기록을 요구한다). 그 밖의 품목은 이유를 보여 주고 재고 화면으로 안내한다.
- 입고 등록은 기존 등록 창을 입력한 이름·수량·용량으로 채워서 연다. 저장은 그 창에서 한다.
- 구매 요청은 입력한 이름과 수량으로 보낸다. 재고 기록과 연결하면 그 기록의 브랜드·용량·CAS 번호가 함께 들어간다. 다른 이름으로만 찾은 기록은 연결 후보로 내놓지 않는다.
- 폐액통 수거 요청은 폐기 문구라 AI로 가지 않는다. 앱이 정해진 문구 패턴으로 알아보고, `POST /api/agent/mode`로 **스위치만** 물은 뒤(문장은 보내지 않는다) `actions`일 때 제안한다. 아니거나 물어보지 못하면 예전처럼 고정 안내 카드가 나온다.

### 폐액 배치 한 문장 구성 (5단계)

- 폐기 문구가 있는 문장에 **이름과 양이 함께 적힌 성분**이 있으면(`src/features/agent/parseWasteComponents.ts`) 그 성분들을 폐액 배치에 담을지 묻는다. 양이 없는 성분은 읽지 않고, 카드가 그렇게 알린다.
- 성분 이름만 일반 검색과 같은 물질 조회로 찾는다. 문장은 어디에도 보내지 않고, AI 분류도 쓰지 않는다(규칙 기반 분류만).
- 이름으로 찾은 물질은 "확인 필요"로 담긴다. 검토 화면이 기존처럼 물질이 맞는지 확인을 요구한다. 입력한 CAS 번호와 일치한 물질만 확인된 것으로 담는다.
- 같은 이름에 여러 형태가 있으면(예: 농도가 다른 염산) 고르게 한다. 찾지 못한 성분은 담지 않고 그렇게 표시한다.
- 확인하면 성분을 폐액 배치 초안(이 기기에만 저장)에 담고 검토 화면을 연다. 폐기 판정은 검토 화면의 규칙 엔진이 한다. 카드에는 분류나 폐기 방법이 나오지 않는다.
- 초안은 서버에 저장되지 않으므로 런타임 스위치와 무관하게 동작한다.

## 지키는 규칙

- **AI는 "어떤 기능 + 어떤 조건"만 고른다.** 서버(`/api/agent/query`)는 연구실 데이터를 읽지 않고 아무것도 저장하지 않는다. 조회와 계산은 앱이 로그인한 사용자의 권한으로 한다. 이용 기록도 서버가 아니라 앱이 요청이 끝난 뒤 DB 함수로 남긴다("측정" 절).
- **응답에 자유 문장 칸이 없다.** 화면의 수치와 이름은 모두 연구실 데이터에서 그린다.
- **폐기·혼합·희석·중화·배수·폐액통 문구는 AI에 보내지 않는다.** 앱과 서버가 각각 걸러 낸다. 판별식은 음성 엔드포인트의 규칙(`DISPOSAL_SAFETY_PATTERNS`)과 같다. 음성 규칙이 바뀌어 둘이 어긋나면 `src/features/agent/agentGuard.test.ts`가 실패한다.
  - 기록을 묻는 문장(폐액통 현황, 기간별 폐기 기록)은 앱이 정해진 문구 패턴으로 알아보고 연구실 기록에서 답한다. 서버를 부르지 않는다.
  - 이름과 양이 함께 적힌 성분이 있으면 폐액 배치 구성 제안으로, 폐액통 수거를 요청하면 수거 요청 제안으로 간다. 둘 다 앱의 정해진 규칙이 정한다.
  - 그 밖에 버리는 방법을 묻거나 무언가를 해 달라는 문장("어떻게", "부어도")은 고정된 안내 카드(폐액 배치 검토 열기, 폐기 기록 보기)로 끝난다.
- **물질명·CAS·제품번호만 입력하면 AI를 부르지 않고 일반 검색으로 넘긴다.**
- **CAS 번호는 사용자가 직접 입력했고 체크섬이 맞을 때만 쓴다.** 시약 이름도 사용자가 입력한 문구에 그대로 있어야 한다.
- **요청 문장은 로그에 남기지 않는다.** 서버 로그에는 계획 종류, 모델, 토큰 수, 소요 시간만 남는다.
- **여러 품목이 일치하면 하나를 고르지 않고 모두 보여 준다.**
- **쓰기는 확인 후에만 한다.** AI는 "무엇을 기록하자는 요청인지"만 고르고, 저장은 사용자가 제안 카드의 버튼을 누른 뒤 앱이 기존 경로로 한다.

## 서버

- 호출 제한: 사용자당 분당 6회(`AGENT` 구간), 하루 `dailyQuota`회. 제한 서비스가 응답하지 않으면 요청을 거부한다.
- AI 호출: 요청당 1회, 출력 500토큰, 제한 시간 8초, 재시도 1회. 모델은 `OPENAI_RESPONSES_MODEL`을 따르고, `OPENAI_AGENT_MODEL`로 따로 지정할 수 있다.
- 폐기 문구와 단순 물질명은 하루 횟수를 쓰지 않는다.
- 기록 제안 기능(`log_usage`, `register_item`, `request_purchase`)은 KV `mode`가 `actions`일 때만 AI에게 선택지로 준다. `read_only`에서는 프롬프트에 나오지 않고, 모델이 돌려줘도 스키마에서 걸러진다.
- `POST /api/agent/mode`: 로그인한 사용자에게 스위치 값(`off`·`read_only`·`actions`)만 알려 준다. 요청 문장을 받지 않고, 읽거나 쓰는 것이 없다. 같은 `AGENT` 호출 제한을 쓴다.

## 측정

요청이 끝날 때마다 앱이 `record_agent_query_event_v1`로 `agent_query_events`에 한 건을 남긴다. 이 기록이 에이전트 모드를 계속 키울지 판단하는 근거다.

| 칸 | 값 |
|---|---|
| `route` | `planner`(AI가 계획을 고름), `rule`(앱의 정해진 규칙: 물질명 넘김, 폐기 문구, 폐액 기록 질문) |
| `kind` | 계획 종류(`item_lookup`, `expiry_list`, `admin_tasks`, `container_status` 등). 물질명만 입력해 넘긴 경우 `identifier`, 계획을 받기 전에 실패하면 `planner` |
| `outcome` | `answered`(내용 있는 카드), `empty`(해당 없음 카드), `no_match`(찾는 시약이 기록에 없음), `navigated`(화면 열기), `handoff_search`(일반 검색으로 넘김), `disposal_card`(폐기 고정 안내), `proposed`(제안 카드를 보여 줌), `confirmed`(제안을 확인해 저장함. 새 요청 ID의 별도 행), `unavailable`(권한·조건이 안 맞는 화면), `unsupported`(처리하지 못하는 요청), `error` |
| `reason` | 보조 코드. 예: `alias_only`, `inventory_empty`, `partial`, `out_of_scope`, `low_confidence`, `capability_disabled`, `admin_only`, `quota_exceeded`, `rate_limited`, `failed` |
| `latency_ms` | 입력을 보낸 때부터 결과를 그릴 때까지(계획 + 기록 조회) |
| `failed_text` | `outcome`이 `unsupported`·`no_match`일 때만. 이메일·URL·전화번호·토큰 형태를 가리고 300자까지 |

- **처리한 요청의 문장은 저장하지 않는다.** 앱이 보내지 않고, DB 함수가 지우고, CHECK 제약이 막는다. 폐기 문구는 `disposal_card`라 문장이 남지 않는다.
- 결과를 보기 전에 다른 요청으로 바꾸거나 지운 요청은 기록하지 않는다. 화면에 답이 나온 요청만 센다.
- 기록 실패는 답에 영향을 주지 않는다. 함수가 없는 환경(migration 미적용)에서는 첫 실패 뒤 그 세션 동안 기록을 시도하지 않는다.
- 같은 요청 ID는 한 번만 저장한다. 계정당 하루 500건을 넘으면 더 저장하지 않는다.
- 조회: RLS를 켜고 정책을 두지 않았고 클라이언트 역할에는 테이블 권한이 없다. 앱에서는 본인도 읽을 수 없고, SQL 편집기(서버 역할)로만 본다. 운영 콘솔 화면은 아직 없다.
- 보관: 자동 삭제 기간 없음. 회원 탈퇴 시 삭제(`ON DELETE CASCADE`), 연구실 삭제 시 연구실 연결만 지움(`ON DELETE SET NULL`).

지표를 보는 SQL(운영 DB에서 읽기 전용으로 실행):

```sql
-- 최근 30일 결과 분포와 해결률(답·이동 / 전체), 지연
select outcome, count(*) as requests,
       round(100.0 * count(*) / sum(count(*)) over (), 1) as percent,
       percentile_cont(0.5) within group (order by latency_ms) as p50_ms,
       percentile_cont(0.95) within group (order by latency_ms) as p95_ms
from public.agent_query_events
where created_at >= now() - interval '30 days'
group by outcome order by requests desc;

-- 처리하지 못한 요청의 문장(다음에 만들 기능의 후보)
select created_at, kind, outcome, reason, failed_text
from public.agent_query_events
where failed_text is not null and created_at >= now() - interval '30 days'
order by created_at desc limit 200;
```

- 해결률은 `answered + empty + navigated`를 전체로 나눈 값으로 본다. `handoff_search`와 `disposal_card`는 에이전트가 필요 없던 요청이므로 따로 본다(비율이 높으면 전환 제안 문구를 고친다).
- 에이전트 사용 비율은 같은 기간의 검색 분석 이벤트 수와 비교한다.
- 제안 수락률은 종류(`kind`)별로 `confirmed` 건수를 `proposed` 건수로 나눈 값이다. 취소하거나 그냥 둔 제안은 행이 없다.

  ```sql
  select kind,
         count(*) filter (where outcome = 'proposed') as proposed,
         count(*) filter (where outcome = 'confirmed') as confirmed
  from public.agent_query_events
  where created_at >= now() - interval '30 days' and outcome in ('proposed', 'confirmed')
  group by kind order by proposed desc;
  ```
- 폐액 배치 구성(`waste_batch`)은 성분을 하나도 찾지 못해도 `empty`로 남긴다. 폐기 문구는 어떤 경우에도 문장을 저장하지 않는다.

## 켜는 순서

1. 개인정보처리방침(2026-11-27 갱신분: 에이전트 모드에 입력한 문장의 AI 전송, 이용 기록, 처리하지 못한 요청의 문장 저장)이 기능보다 먼저 또는 함께 배포돼야 한다. 문구는 이 저장소에 들어 있다. `APP_STORE_PRIVACY_DISCLOSURE.md`의 "에이전트 모드" 절에 따라 두 스토어 응답도 고친다.
2. migration `20261127080000_agent_query_events.sql`을 Staging과 운영 DB에 연달아 적용한다(두 환경의 이력이 어긋나면 배포 검사가 막는다). 적용하지 않아도 에이전트는 동작하지만 기록이 남지 않는다.

Hosted 검사(`npm run security:supabase-advisors:hosted`)는 로컬에 토큰이 없어 돌리지 않았고, 배포 workflow에서 처음 돈다.

3. Staging KV에 스위치를 넣는다. 기존 `runtime_config`와 `ai_decisions_config`는 건드리지 않는다.

   ```json
   { "mode": "read_only", "dailyQuota": 100 }
   ```

   `mode`는 `off`, `read_only`, `actions` 중 하나다. `read_only`로 조회를 먼저 확인한 뒤 `actions`로 올리면 기록 제안이 켜진다. `dailyQuota`는 1~1000이다. `expiresAt`(ISO 시각)을 넣으면 그 시각 뒤에 꺼진다. 형식이 틀리거나 모르는 칸이 있으면 꺼진 것으로 본다.
4. Staging 플래그 `VITE_ENABLE_AGENT_MODE`를 `true`로 켜고 배포한다.
5. "확인할 것"을 Staging에서 확인한다.
6. 운영 KV에 같은 값을 넣고, 운영 플래그를 같은 값으로 켠 뒤 운영 배포를 한다(운영 승격은 Staging과 플래그가 같아야 통과한다).

## 끄는 방법

- 빠른 차단: KV의 `mode`를 `off`로 바꾸거나 키를 지운다. 전환 버튼은 남지만 요청하면 "아직 켜져 있지 않아요"가 나온다.
- 기록 제안만 차단: KV의 `mode`를 `read_only`로 내린다. 이미 화면에 떠 있는 제안은 그대로 확인할 수 있고(저장은 기존 경로의 권한 검사를 그대로 받는다), 새 제안은 나오지 않는다.
- 스위치와 무관한 것: 폐액 기록 질문, 폐기 고정 안내, 폐액 배치 구성 제안은 서버를 부르지 않으므로 KV로 꺼지지 않는다. 이들은 플래그를 꺼야 사라진다.
- 완전히 숨김: 플래그를 `false`로 바꿔 다시 배포한다. 검색 화면이 이전과 같아진다.

## 확인할 것

- 플래그를 끈 빌드에서 검색 화면에 전환 버튼과 제안 줄이 없는지.
- 로그인하지 않고 에이전트를 누르면 로그인으로 가고, 로그인 뒤 에이전트 모드로 돌아오는지.
- 실제 OpenAI 응답으로 `scripts`의 고정 문장 세트를 돌려 계획 정확도를 확인한다(세트는 다음 단계에서 추가). 로컬에는 OpenAI 키가 없어 1단계의 AI 경로는 모킹한 응답으로만 검증했다.
- 폐기 문구("아세톤 어떻게 버려?")가 고정 카드로 끝나는지. 서버로 직접 보낸 폐기 문구는 Cloudflare 로그에 `route: guard`로 남는다.
- `read_only`에서 "아세톤 30% 남았다고 기록해줘"가 "처리하지 못하는 요청"으로, "폐액통 수거 요청해줘"가 고정 카드로 끝나는지. `actions`로 올린 뒤에는 둘 다 제안 카드가 나오는지.
- 제안 카드에서 취소하면 아무것도 바뀌지 않고, 확인하면 재고·구매 요청·폐액통 화면에 그대로 반영되는지. 같은 이름의 병이 둘이면 고르기 전에 버튼이 눌리지 않는지.
- 제안을 띄운 채 다른 연구실로 바꾸면 카드가 지워지는지.
- "아세톤 200mL랑 메탄올 100mL 섞은 폐액"이 두 성분을 "확인 필요"로 보여 주고, 담으면 검토 화면이 열려 물질 확인을 요구하는지.
- `agent_query_events`에 제안은 `proposed`, 확인은 `confirmed`로 따로 남는지.
- 다른 연구실로 바꾸면 이전 결과가 지워지는지.
- 개인 공간에서 관리자 화면·일상점검·구매 요청을 열어 달라고 하면 "연구실을 선택해야" 안내가 나오는지.
- 휴대폰 폭에서 전환 버튼이 검색창 위에 놓이고 결과가 가려지지 않는지.
- 요청 몇 건(답이 나온 것, 화면 열기, 폐기 문구, "오늘 날씨 알려줘", 없는 시약 이름) 뒤 `agent_query_events`에 한 건씩 남고, `failed_text`가 마지막 두 건에만 있는지.
- 시험 계정을 탈퇴시킨 뒤 그 계정의 `agent_query_events` 행이 남지 않는지.

## 남은 일

- 2차 후보: 내보내기 바로가기(점검 대비 엑셀, 위험분석 목록, 폐기 기록, QR 라벨), 보관 적합성 질의, 조건 묶음 일괄 이동, 음성 시트 통합
- 실제 OpenAI 응답으로 계획 정확도를 재는 고정 문장 세트(`scripts`)는 아직 없다. 기록 제안을 켜기 전에 만들어 돌린다.
- 알려진 한계
  - "처리해", "mix" 같은 단어가 들어가면 폐기와 무관한 문장("PCR master mix 어디 있어?")도 폐기 안내 카드로 간다. 규칙을 유지하기로 한 결과다.
  - 시약장에 놓인 재고 품목 중 재고 표에서 온 줄은 시약장을 열 때 병을 강조하지 못한다.
  - 조건이 안 맞아 닫힌 기능을 물으면(예: 관리자가 아닌데 "할 일 알려줘") 이유 없이 "아직 처리하지 못하는 요청"으로만 나온다.
  - 폐기 기록 요약은 한 번에 최근 1,000건까지만 합친다. 넘으면 카드에 표시한다.
  - 폐기 기록을 "뭐 버렸어?"처럼 물으면 기록 질문으로 알아보지 못하고 고정 안내 카드로 간다.
  - 이용 기록을 보는 화면이 없다. 지표는 "측정" 절의 SQL로 본다.
  - 폐액 배치 구성은 양이 함께 적힌 성분만 읽는다. 질량(g)으로 적은 양과 농도는 담기지 않고 검토 화면에서 입력한다. "오늘 쓴 아세톤 200mL"처럼 이름 앞에 다른 말이 붙으면 그대로 조회해 "찾지 못함"으로 끝난다(다른 물질로 잘못 찾는 것보다 낫다고 보았다).
  - "다 쓴 병" 기록은 시약장 선반에 놓인 병만 된다.
  - 성분 수량의 숫자가 이름에도 들어 있으면("2-프로판올 구매 요청") 수량으로 잘못 채워질 수 있다. 카드에서 고칠 수 있다.
  - pgTAP 테스트(`supabase/tests/agent_query_events_behavior.sql`)는 로컬에 Docker가 없어 CI에서만 돈다. 같은 동작은 `src/features/agent/agentEventsDatabase.test.ts`가 실제 migration을 pglite에 적용해 확인한다.

## 화면 규칙과 Astryx 기준 대조

에이전트 결과 화면의 스타일은 `src/features/agent/agentCardStyles.ts` 한 곳에 있다. 2026-11-27에 Astryx(`meta/astryx`, Meta의 디자인 시스템) 기준으로 점검해 고쳤다.

### 무엇을 기준으로 삼았나

- **스킬 원문**(`plugins/astryx/skills/astryx/SKILL.md`): Astryx CLI로 화면을 만드는 방법을 안내하는 짧은 문서다. "Astryx를 쓰지 않는 기존 앱은 사용자가 요청하지 않는 한 현재 UI 스택을 유지한다"고 적혀 있어, 스킬을 설치하거나 `@astryxdesign` 패키지를 들이지 않았다. 납품 전 점검 항목(하드코딩한 hex·px 값, 따로 불러온 CSS·`@apply`를 토큰으로 바꾸고, 빌드한 결과를 낸다)은 그대로 적용했다.
- **Component Audit Rubric 1.16.6**과 **Accessibility Checklist**(11항목), **Design Conventions**, **Container Padding System**(저장소 위키): 스킬이 가리키는 실제 평가 기준이다. Astryx 라이브러리 자체를 감사하는 문서라 토큰 이름·`themeProps`·StyleX·`.doc.mjs`·스토리북·changeset 같은 항목은 이 앱에 해당하지 않는다. 어느 웹 UI에나 적용되는 항목만 아래에 대조했다.
- 기준표는 점수를 Astryx 컴포넌트에만 매긴다고 밝히고 있어 등급(A~F)은 내지 않았다. 대신 항목별 판정과 근거를 적는다.

### 확인하지 못한 것

axe 자동 검사, 실제 스크린리더, WebKit(이 점검은 Chromium에서만 측정), 사용자 지정 테마(앱에 없음). 화면 캡처는 검토에만 쓰고 저장소에 남기지 않았다.

검색 화면과 함께 쓰는 부분(검색창, 전송 버튼, 모드 전환, 자동완성 목록)은 이번 범위가 아니라 고치지 않았다. 에이전트가 추가한 "에이전트에게 묻기" 줄만 논리 속성과 알파 틴트로 맞췄다.
