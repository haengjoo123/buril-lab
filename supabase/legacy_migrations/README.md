# 이전 마이그레이션 보관소

이 폴더는 2026-08-24 기준선 전환 전에 저장소에 있던 SQL과 계약 시험을 보관합니다.
여기의 SQL은 새 데이터베이스에 순서대로 실행하지 않습니다. 새 설치의 시작점은
`supabase/migrations/20260824000000_production_baseline.sql`입니다.

## 기준선 원칙

- 운영 데이터베이스의 실제 스키마, 함수, 권한, 정책, 인덱스, Storage 설정을 기준으로 기준선을 만들었습니다.
- `application-history-before-baseline.json`은 전환 전 로컬/운영 적용 이력을 읽기 전용으로 보관합니다.
- 운영 데이터와 스키마에는 기준선 SQL을 실행하지 않습니다. 복구 시험이 끝난 뒤 적용 이력만 정리합니다.
- 운영 적용 이력 정리는 `scripts/repair-production-migration-history.ps1`만 사용합니다. 먼저 `plan -ProjectRef <ref>`로 원격 이력이 검토된 89개 버전과 정확히 같은지 확인하고, 출력된 해시를 포함한 확인문구로만 `apply`를 실행합니다.
- 스크립트는 89개 remote 버전의 정규화 SHA-256과 local/remote 표시·시각을 포함한 전체 118행 증거 SHA-256을 별도로 고정합니다. 개수만 같거나 일부만 같은 이력은 중단합니다. 출력 증거에는 개수·해시·상태만 포함되고 DB 비밀번호와 CLI 원문은 포함되지 않습니다.
- DB 비밀번호는 명령줄 인자로 노출하지 않고, Supabase CLI 공식 `SUPABASE_DB_PASSWORD` 프로세스 환경변수로만 일시 전달한 뒤 원래 값으로 복원합니다.
- 도구는 검토한 Supabase CLI `2.115.0`을 `npx --no-install`로만 실행하며 작업 중 임의 버전을 내려받지 않습니다.
- 되돌릴 때는 같은 스크립트의 `restore-legacy` 모드를 사용합니다. 중간에 중단되면 기준선+89개인 정확한 전이 상태에서 `apply` 또는 `restore-legacy`를 다시 선택할 수 있습니다.

## 새 변경 순서

새 구조 추가 → Staging 적용 및 시험 → 앱 전환 → 사용 확인 → 이전 구조의 실행 권한 회수 순서로 진행합니다.
테이블·열·함수 삭제는 추가와 같은 운영 배포에 넣지 않습니다.
